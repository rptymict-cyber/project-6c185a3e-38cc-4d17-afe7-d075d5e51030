# AGDICT 개발자 DS 댓글 대응 워크플로우

이 문서는 Claude Code와 Codex가 공통으로 참조하는 개발자 DS 댓글 대응의
**단일 실행 기준**이다. `AGENTS.md`와 `CLAUDE.md`에는 이 문서로 향하는 짧은
포인터만 유지한다. 고정 서비스 식별값은 같은 폴더의
[`RESOURCES.md`](RESOURCES.md)를 따른다.

## 1. 목적

개발자가 Confluence에 남긴 사양서 변경 요청을 현재 사양과 실제 구현에 대조해
검증하고, 사용자가 바로 이해하고 수정·회신할 수 있는 형태로 정리한다.

핵심 원칙:

1. 개발자 요청은 가능한 범위에서 정확하게 반영한다.
2. 현재 Confluence·GitHub·Lovable과 직접 충돌하는 수정은 막는다.
3. GitHub 코드만 보고 `Lovable 확인 완료` 또는 `앱 화면 확인 완료`라고 하지 않는다.
4. 현재 DS에 이미 같은 의미가 있으면 중복 수정하지 않는다.
5. 분석과 외부 시스템 실행을 분리하고, 실행은 사용자의 명시적 승인 뒤에 한다.

## 2. 입력

개발자 댓글 원문, Confluence 링크, DS No., 현재 사양서 문구, 개발자가 제시한
파일·라인·Baseline·기술근거 또는 코드 스니펫 중 하나 이상을 받을 수 있다.
한 댓글에 여러 요청이나 DS No.가 있으면 반드시 각각 독립적으로 판정한다.

## 3. 강제 검증 순서

1. **요청 분리**: 댓글을 요청 및 DS No. 단위로 나눈다.
2. **Confluence 현재 DS 확인**: DS No., 상세 사양 전체, 비고와 기술근거,
   같은 의미가 다른 DS에 이미 있는지 확인한다.
3. **GitHub `main` 확인**: HEAD SHA와 실제 렌더링 파일, 라우트, 관련 컴포넌트,
   공통 토큰, 화면별 분기, import 및 미사용 컴포넌트 여부를 확인한다.
4. **Lovable 현재 구현 확인**: GitHub에서 확인한 핵심 파일을 Lovable에서도 직접
   읽고 관련 컴포넌트와 토큰 적용 여부를 확인한다.
5. **Lovable ↔ GitHub 동기화 확인**: Lovable 최신 edit/commit SHA와 GitHub
   `main` HEAD SHA를 비교하고, 댓글 관련 핵심 파일 내용도 양쪽에서 교차 확인한다.
6. **개발자 근거 파일 확인**: `docs/spec/gap/...`, `docs/drift/...`, 정책·티켓 문서
   등 제시된 자료의 존재와 내용을 확인한다.
7. **공통 정책 확인**: `AGENTS.md`, `CLAUDE.md`, 공통 토큰과 프로젝트 컨벤션을
   확인한다.
8. **요청별 판정과 할 일 결정**: 5장의 6개 상태만 사용하며 상태와 액션을 분리한다.
9. **사용자용 답변 작성**: 7장의 고정 형식을 따른다.

핵심 소스에 접근할 수 없으면 확인된 소스와 미확인 소스를 명확히 구분하고,
접근하지 못한 자료를 확인했다고 표현하지 않는다.

## 4. 소스별 확인 기준

### 4.1 Confluence 현재 DS

- DS No., Section명, Screen ID, 구분(Visible/Invisible/Design)을 확인한다.
- 상세 사양 전체와 비고의 `Route / File / Baseline / 기술근거`를 읽는다.
- `신규 기재` 요청도 같은 의미가 이미 있으면 중복 수정하지 않는다.
- 지정한 DS No.가 현재 다른 의미의 행이면 임의로 덮어쓰지 않는다.

### 4.2 GitHub `main`

- 오래된 문서보다 현재 `main` 실제 코드를 우선한다.
- 지목된 파일뿐 아니라 실제 렌더링 파일과 라우트까지 확인한다.
- 보조 문서가 없어도 실제 코드로 검증할 수 있으면 판정을 계속한다.

### 4.3 Lovable 현재 구현

- GitHub에서 본 동일 파일을 Lovable에서 직접 조회한다.
- Lovable 코드 확인과 프리뷰 화면 시각 확인을 구분한다.
- 코드를 읽었을 뿐이면 `Lovable 현재 코드 기준`이라고 표현한다.
- 프리뷰나 스크린샷을 실제로 보지 않았다면 픽셀·렌더링 상태를 확인했다고 말하지
  않는다.

### 4.4 동기화 판정

- SHA 동일: 같은 커밋을 가리킨다. 핵심 파일도 교차 확인한 뒤
  `Lovable ↔ GitHub main 동일 커밋 상태 확인`이라고 표현할 수 있다.
- SHA 불일치: 동기화 불일치로 기록하고 관련 파일을 양쪽에서 각각 읽는다.
  어느 쪽이 정본인지 자동 추정하지 않는다.
- 코드 동기화는 프리뷰 화면 시각 검증을 뜻하지 않는다.

### 4.5 개발자 근거 파일

- 존재하면 내용을 읽고 보조 근거로 사용한다.
- 없으면 `현재 GitHub main에서 찾을 수 없음`이라고 기록한다.
- 파일 부재만으로 `근거 불일치`로 판정하지 않는다.
- 실제 코드로 검증 가능하면 계속하고, 불가능하면 보류 또는 확인 불가로 판정한다.

### 4.6 정책·토큰 주장

개발자가 `전역 정책`, `앱 토큰이 정본`, `G-palette`, `G-price-color` 등을 근거로
제시하면 실제 저장소와 Confluence에서 근거를 찾는다. 정책상 미래 목표값과 현재
앱 실제값을 구분한다. 현재 화면에 하드코딩 값이 적용돼 있다면 `현재 앱 실제값`
판정에서는 그 값을 사용한다.

## 5. 판정 체계

- `🟢 이미 반영`: 현재 DS 또는 구현에 동일 의미가 이미 있다.
- `🟠 사양서 수정 필요`: Lovable/GitHub 실제 구현과 요청이 일치하고 현재 DS만
  다르다.
- `🔵 Lovable 수정 필요`: 현재 DS가 맞고 Lovable 구현이 다르다.
- `🔴 근거 불일치`: 개발자 핵심 주장과 현재 실제 자료가 직접 충돌한다.
- `🟡 판정 보류`: DS No. 재지정, 정책 결정, 근거 보완 등 추가 판단이 필요하다.
- `⚪ 확인 불가`: 필수 자료에 접근할 수 없다.

`판정`은 상태 분류이고 `할 일`은 실제 액션이다. 사용자 답변에서는 반드시 별도
열로 보여준다. 애매한 경우 사양서와 앱을 동시에 수정하지 않는다.

## 6. 로컬 변경과 변경 이력

### 6.1 변경 이력 로그

실제 반영이 승인되면 배치 전체를 다음 파일에 기록한다.

`docs/ds/dev-comments/{yyyy-mm-dd}-{리뷰어 또는 배치 슬러그}.md`

```markdown
# {date} 개발자 댓글 대응 — {리뷰어명}

원본 스레드: {Confluence 페이지 URL 또는 pageId#commentId}

## DS-XXXXX ({판정})
- 메뉴: {menuId와 DS 파일}
- 수정 전: "{구분·상세 사양·비고를 포함한 원문 전체}"
- 수정 후: "{구분·상세 사양·비고를 포함한 변경문 전체}"
- 근거: {개발자 근거와 직접 재검증한 결과}
- 처리: {검증·Confluence 버전·커밋·대기 상태}
- 회신 초안: "..."

## 보류
- DS-XXXXX: {사유와 필요한 추가 자료 또는 결정}
```

### 6.2 사양서 수정 규칙

- 정확히 해당 DS No. 행만 편집하고 다른 행을 재정렬하거나 재번호하지 않는다.
- 수정 전 원문의 구분·상세 사양·비고 전체를 로그에 보존한다.
- 구분 값은 지적된 범위만 바꾸며, 범주 변경이 필요하면 먼저 사용자에게 확인한다.
- 비고의 `Route / File / Baseline / 기술근거.NN` 형식을 유지한다.
- 수정 후 순서대로 실행한다.
  1. `node docs/ds/scripts/validate-ds.mjs <menuId>`
  2. `node docs/ds/scripts/md-to-confluence.mjs <menuId>`
  3. 필요 시 `node docs/ds/scripts/deliver-ds.mjs <menuId> --mode=cloud`
- `docs/ds/ds-menu-progress.md`의 해당 메뉴 상태도 함께 갱신한다.

### 6.3 앱(Lovable) 수정 규칙

- `AGENTS.md`와 `CLAUDE.md`의 전역 컨벤션을 먼저 확인한다.
- 댓글이 지적한 DS No. 해결에 필요한 최소 범위만 수정한다.
- 수정 후 관련 화면을 dev 서버에서 열어 동작을 확인한다.
- 앱 수정과 사양서 수정은 별도 커밋으로 분리하고 커밋 메시지에 DS No.를 쓴다.
- 이미 게시된 Git 히스토리를 force-push, rebase, amend, squash하지 않는다.

## 7. 사용자 응답 기본 형식

항상 다음 순서를 기본으로 한다.

### ① 🔑 쉬운 상황 요약

댓글 전체에 대해 한 번만 설명하며 다음을 포함한다.

- 개발자가 왜 댓글을 달았고 무엇을 바꾸려는지
- 현재 Confluence·GitHub·Lovable 확인 결과
- Lovable/GitHub 동기화 상태
- 실제로 수정할 것과 유지·보류할 것

### ② 개발자 댓글 처리 결과

| 요청 | 판정 | 할 일 |
|---|---|---|
| ... | ... | ... |

### ③ 내가 실제로 수정할 사양서

`🟠 사양서 수정 필요`만 포함하고 각 DS를 독립 블록으로 작성한다.

````markdown
📍 위치: <메뉴 › DS No. › 항목>

#### [검색어]
```markdown
<현재 검색 문구>
```

#### [변경 전]
```markdown
<현재 Confluence 원문 전체>
```

#### [변경 후]
```markdown
<최종 교체 문장 또는 행 전체>
```

#### [확인용 검색어]
```markdown
<저장 후 검색 문구>
```
````

수정할 DS가 없으면 `이번 건에서 실제 수정할 사양서: 없음`이라고 쓴다.

### ④ 추가 확인/보류

`🔴 / 🟡 / ⚪`만 표시한다. 현재 무엇과 충돌하는지와 어떤 자료·결정이 더
필요한지를 짧게 쓴다.

### ⑤ 개발자에게 남길 댓글

복사해 붙여넣을 수 있는 업무체 문안으로 작성하며 다음을 포함한다.

- 요청별 처리 결과와 실제 수정한 DS No.
- 변경 전후 핵심 값
- 이미 반영돼 수정하지 않은 DS No.
- 보류 또는 근거 불일치 DS No.
- Lovable 수정 여부와 GitHub 수정 여부
- Lovable ↔ GitHub 동기화 여부

### ⑥ 참고 근거

기본 3~5줄로 Confluence 현재 DS, GitHub `main`, Lovable 현재 파일, SHA 및 핵심
파일 일치 여부, 개발자 근거 파일 존재·부재를 요약한다.

## 8. Lovable 수정 프롬프트

`🔵 Lovable 수정 필요`일 때만 작성한다. `AGENTS.md` 지침에 따라 핵심이 명확하고
불필요한 탐색·재작업을 줄이는 저크레딧 프롬프트로 만든다.

```markdown
[Lovable 수정 요청]

대상:
- 화면/기능:
- 파일:
- 컴포넌트/함수:

현재:
- <현재 Lovable 실제 구현>

변경:
- <필요한 최소 수정>

검증 기준:
- <수정 후 상태>

유지:
- <관련 없는 기존 기능>

관련 없는 부분은 건드리지 말아 주세요.
```

추측한 파일이나 값을 넣지 않는다.

## 9. 실행 승인 경계

- `추천안으로 하자`, `이렇게 하자` → 방향 결정이며 실행 승인이 아니다.
- `사양서에 반영해줘` → Confluence 수정 승인이다.
- `이 문안으로 댓글 게시해줘` → 댓글 게시 승인이다.
- `Lovable에 적용해줘` → Lovable 수정 승인이다.

명시적 승인 전에는 Confluence 수정, 댓글 게시, Lovable 수정, git push처럼 외부에
영향을 주는 작업을 실행하지 않는다. 로컬 초안·로그 작성과 검증은 요청 범위에서
수행할 수 있다.

## 10. 실행 후 재검증

- Confluence 수정 후: 새 값 존재, 이전 값 교체, 다른 DS 손상 없음 확인.
- Lovable 수정 후: 대상 파일 변경, 관련 없는 파일 미변경, GitHub 동기화 재확인.
- 댓글 게시 후: 원 스레드에 실제 새 답글이 생성됐는지 확인.
- 성공 응답이나 재조회 결과를 확인하지 못하면 완료라고 말하지 않는다.

## 11. 표현 규칙

사용 가능: `Lovable 현재 코드 확인`, `Lovable 관련 파일 직접 조회`,
`Lovable/GitHub SHA 동일 확인`, `관련 파일 내용 동일 확인`.

실제 프리뷰나 스크린샷을 보지 않았다면 `Lovable 화면 실측 완료`,
`앱 화면 픽셀 확인 완료`, `웹과 앱이 완전히 동일`,
`실제 렌더링 화면까지 완전히 동일`이라고 표현하지 않는다.

## 12. MCP 접근 실패와 보안

- 인증 만료, 권한 없음, Connector 미지원, 일부 소스만 접근 가능 상태를 구분한다.
- 핵심 소스를 확인하지 못하면 억지로 결론내리지 않는다.
- PAT, Atlassian API Token, Lovable 인증 토큰, 비밀번호, 세션 쿠키, `.env` 비밀값,
  API Key는 저장하거나 출력하지 않는다.
- 프로젝트 ID, 저장소 이름, Page ID, 공개 URL만 고정 문서에 보관한다.

## 13. 최종 자체 검수

- [ ] 댓글을 요청 및 DS No.별로 분리했는가
- [ ] Confluence 현재 DS 원문을 직접 확인했는가
- [ ] GitHub `main` 실제 파일과 HEAD SHA를 확인했는가
- [ ] Lovable 현재 파일과 최신 SHA를 직접 확인했는가
- [ ] 댓글 관련 핵심 파일을 양쪽에서 교차 확인했는가
- [ ] 코드 확인과 화면 시각 확인을 구분했는가
- [ ] 개발자 근거 파일의 존재와 내용을 확인했는가
- [ ] 근거 파일이 없어도 실제 코드로 검증을 계속했는가
- [ ] 이미 같은 의미가 현재 DS에 있는지 확인했는가
- [ ] 개발자 핵심 주장과 실제 구현 충돌 여부를 확인했는가
- [ ] 판정은 6개 상태 중 하나이고 `판정`과 `할 일`을 분리했는가
- [ ] 쉬운 상황 요약과 3열 결과표가 있는가
